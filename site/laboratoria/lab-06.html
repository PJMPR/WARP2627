01

CELE LABORATORIUM

Po spotkaniu potrafisz

  • Zbudować poprawny dokument HTML z deklaracją <!doctype html>, sekcjami head i body.
  • Rozróżnić metadane dokumentu od treści widocznej w przeglądarce.
  • Stosować nagłówki, akapity, listy, tabele, linki, kod i podstawowe znaczniki semantyczne.
  • Połączyć wszystkie dokumenty ze wspólnym arkuszem CSS i zbudować spójny wygląd serwisu.
  • Stylować akapity, listy, tabele, nawigację i bloki kodu z zachowaniem czytelności.
  • Łączyć kilka stron przy użyciu linków względnych i poprawnej struktury katalogów.
  • Sprawdzić dokument w przeglądarce i walidatorze HTML.
  • Rozwijać stronę na branchach, wykonywać review i scalać Pull Requesty.
  • Opublikować statyczną stronę z gałęzi main przez GitHub Pages bez GitHub Actions.
Ograniczenie technologiczne

Używajcie HTML i jednego zewnętrznego arkusza styles.css. Nie stosujcie atrybutu style, znacznika <style>, frameworków CSS ani JavaScriptu. Celem jest samodzielne przećwiczenie struktury HTML, selektorów, klas i podstawowych właściwości CSS.

03

WPROWADZENIE

Anatomia dokumentu HTML

HTML opisuje strukturę i znaczenie treści. Znacznik otwierający, zawartość i znacznik zamykający tworzą element, np. <p>Akapit</p>. Wcięcia nie zmieniają działania strony, ale pomagają zobaczyć zagnieżdżenie elementów.

<!doctype html>
<html lang="pl">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Student IT Knowledge Base</title>
</head>
<body>
  <header>
    <h1>Student IT Knowledge Base</h1>
  </header>
  <main>
    <p>Ściągi z przedmiotów informatycznych.</p>
  </main>
  <footer>
    <p>Materiały edukacyjne</p>
  </footer>
</body>
</html>
ElementRolaWażna uwaga
<!doctype html>Informuje przeglądarkę, że dokument używa współczesnego HTML.To pierwsza linia każdego pliku.
<html lang="pl">Obejmuje cały dokument i określa język treści.Atrybut lang pomaga czytnikom ekranu i wyszukiwarkom.
<head>Zawiera metadane, kodowanie i tytuł karty.Nie umieszczaj tutaj widocznej treści strony.
<body>Zawiera treść wyświetlaną w oknie przeglądarki.W środku umieść strukturę strony.
<header>Wprowadzenie do strony lub sekcji.To nie to samo co <head>.
<nav>Grupa najważniejszych odnośników nawigacyjnych.Umieść w niej menu między stronami.
<main>Główna, unikalna treść dokumentu.Na stronie powinien wystąpić tylko raz.
<section>Tematyczna część dokumentu.Zwykle zaczyna się nagłówkiem.
<footer>Stopka strony lub sekcji.Może zawierać autora lub informację o projekcie.

Elementy, których użyjecie

h1–h3
Nagłówki tworzą logiczną hierarchię. Nie wybieraj poziomu ze względu na rozmiar tekstu.
p
Akapit tekstu. Kolejnych akapitów nie rozdzielaj pustymi znacznikami br.
ul / ol / li
Lista nieuporządkowana, uporządkowana oraz pojedynczy element listy.
table
Tabela danych z caption, thead, tbody, wierszami tr oraz komórkami th i td.

Odnośnik. Atrybut href wskazuje dokument, miejsce w dokumencie albo adres zewnętrzny.

strong / em
Ważność i akcent znaczeniowy — nie narzędzia do dekorowania tekstu.

SPECYFIKACJA WIZUALNA

Zbudujcie spójny i czytelny interfejs

Nie musicie odwzorowywać konkretnego projektu piksel w piksel. Serwis ma jednak wyglądać jak jedna całość. Najpierw ustalcie prosty system wizualny, a następnie stosujcie go konsekwentnie na wszystkich stronach.

  • Kolory: tło strony, powierzchnia elementów, czytelny tekst i jeden kolor akcentu.
  • Typografia: systemowy krój pisma, hierarchia h1–h3 i wygodna wysokość linii.
  • Szerokość: treść ograniczona przez max-width i wyśrodkowana.
  • Odstępy: powtarzalne wartości, np. 8px, 16px, 24px i 32px.
  • Komponenty: wspólny wygląd nawigacji, paneli, list, tabel, kodu i linków.
  • Responsywność: brak poziomego przewijania całej strony przy szerokości około 375 px.
  • Interakcja: linki mają widoczny stan :hover oraz :focus-visible.

WZAJEMNE REVIEW

Otwórzcie dwa Pull Requesty

  1. Każda osoba otwiera PR ze swojego brancha do main.
  2. Student B najpierw sprawdza PR Studenta A: semantykę strony głównej, nazwy klas i wspólny styles.css.
  3. Po poprawkach Student B zatwierdza PR Studenta A i scala go jako pierwszy.

  5. Student A recenzuje zaktualizowany PR Studenta B: HTML, link do dokumentacji, ścieżkę CSS oraz widok szeroki i mobilny.
  6. Po ewentualnych poprawkach Student A zatwierdza i scala drugi PR.

WALIDACJA

Sprawdźcie poprawność HTML

  1. Wejdźcie na validator.w3.org.
  2. Użyjcie zakładki Validate by File Upload i sprawdźcie kolejno cztery pliki HTML.
  3. Sprawdźcie styles.css w walidatorze CSS W3C.
  4. Poprawcie błędy oznaczone jako Error. Przeczytajcie również ostrzeżenia — nie każde wymaga zmiany, ale każde trzeba rozumieć.
  5. Jeśli walidacja wymaga poprawek, utwórzcie branch fix/html-css-validation, wykonajcie commit i przeprowadźcie jeszcze jeden PR.
Nie publikuj danych osobowych

Repozytorium i strona mogą być publiczne. Używajcie nazw kont GitHub lub neutralnego określenia zespołu. Nie umieszczajcie numerów indeksów, prywatnych adresów e-mail, tokenów ani haseł.

    ✓
  • index.html otwiera się lokalnie i prowadzi do wszystkich trzech stron.
  • Każda podstrona pozwala wrócić do strony głównej i korzysta ze wspólnego CSS.
  • W repozytorium pozostały wszystkie wcześniejsze pliki Markdown.
  • Walidatory nie zgłaszają błędów HTML ani CSS.

PUBLIKACJA

Włączcie GitHub Pages bez Actions

Publikację konfiguruje właściciel repozytorium po scaleniu wszystkich potrzebnych zmian do main. Nie twórzcie workflow i nie dodawajcie plików w .github/workflows.

  1. Na GitHubie otwórzcie repozytorium i przejdźcie do Settings → Pages.
  2. W sekcji Build and deployment jako Source wybierzcie Deploy from a branch.
  3. Wybierzcie branch main oraz katalog /(root), następnie kliknijcie Save.
  4. Poczekajcie, aż GitHub pokaże adres opublikowanej strony. Pierwsze wdrożenie może potrwać kilka minut.
  5. Otwórzcie otrzymany adres w nowej karcie i ponownie sprawdźcie wszystkie linki. Nie oceniajcie publikacji wyłącznie na podstawie lokalnego podglądu.
  6. Dodajcie adres działającej strony w polu About → Website repozytorium.
Źródłem jest main

GitHub Pages publikuje tylko stan scalony do main. Sam push brancha roboczego ani otwarty PR nie zmienia publicznej strony.

DIAGNOSTYKA

Najczęstsze problemy

GitHub Pages pokazuje stronę 404

Sprawdź, czy plik nazywa się dokładnie index.html, znajduje się w katalogu głównym gałęzi main, a w Settings → Pages wybrano Deploy from a branch, main i /(root). Po zmianie ustawień odczekaj kilka minut.

Link działa lokalnie, ale nie na GitHub Pages

Sprawdź wielkość liter w nazwie pliku i katalogu. Serwer rozróżnia Bash.html i bash.html. Używaj linków względnych bez początkowego ukośnika, np. pages/bash.html.

Na stronie widać dosłownie znaczniki HTML

Sprawdź, czy zamiast znaków < i > nie wpisano encji &lt; i &gt; w miejscu, w którym miały tworzyć element. Encji używamy wtedy, gdy chcemy pokazać znacznik jako tekst.

Polskie znaki wyświetlają się niepoprawnie

Plik zapisz jako UTF-8 i upewnij się, że w head możliwie wcześnie znajduje się <meta charset="utf-8">.

Tabela „rozsypuje się” w przeglądarce

Każdy wiersz musi być elementem tr, a wewnątrz powinien mieć tę samą liczbę komórek th lub td. Sprawdź domknięcie elementów i wynik walidatora.

Po scaleniu PR-a nie widzę pliku partnera

Scalenie na GitHubie nie aktualizuje automatycznie plików lokalnych. Wykonaj git switch main, git pull --ff-only origin main i ponownie sprawdź katalog projektu.

Link do strony partnera zwraca błąd podczas pierwszego PR-a

To oczekiwane, jeśli drugi plik znajduje się jeszcze na osobnym branchu. Pełne działanie linków sprawdzajcie ponownie po scaleniu obu PR-ów do main.

CSS działa na index.html, ale nie na podstronach

Dokumenty w katalogu pages muszą cofnąć się o jeden poziom. Użyj href="../styles.css" i sprawdź w DevTools → Network, czy arkusz nie zwraca błędu 404.

Tabela poszerza całą stronę na telefonie

Umieść tabelę w elemencie z klasą table-scroll i ustaw dla niego overflow-x: auto. Przetestuj szerokość 375 px w trybie urządzenia DevTools.

Przypadkowo dodano JavaScript lub style inline

Usuń skrypt albo atrybuty style, przenieś potrzebne deklaracje do styles.css, wykonaj kolejny commit i zaktualizuj PR zwykłym git push.
