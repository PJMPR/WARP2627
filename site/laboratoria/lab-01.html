03

GITHUB / KONTO I REPOZYTORIUM

Utwórz zdalne repozytorium

  1. Załóż konto na GitHubie lub zaloguj się na istniejące. Włącz uwierzytelnianie dwuskładnikowe i skonfiguruj logowanie zgodnie z instrukcjami GitHub.
  2. Wybierz New repository, wpisz np. warp-lab01-hello-workshop i ustaw widoczność Public. Utwórz puste repozytorium: nie zaznaczaj tworzenia README, licencji ani .gitignore, bo projekt istnieje lokalnie.
  3. Skopiuj adres HTTPS repozytorium. Nie udostępniaj hasła ani tokenu. Git może otworzyć przeglądarkę, aby uwierzytelnić się przez Git Credential Manager.
Uwaga o prywatności

Publiczne repozytorium jest widoczne dla wszystkich. Nie umieszczaj w nim haseł, tokenów ani prywatnych danych. Adres e-mail autora commitów też może być publiczny; w razie potrzeby ustaw prywatność adresu w GitHubie i użyj podanego adresu noreply.

04

GIT / PIERWSZY PUSH

Zapisz i opublikuj projekt

W terminalu, w katalogu HelloWorkshop, skonfiguruj autora commitów, zainicjuj repozytorium i sprawdź jego stan. Zastąp przykładowe dane własnymi.

# Ustawia globalne dane autora (--global: dla wszystkich repozytoriów na tym komputerze)
git config --global user.name "Imię Nazwisko"
git config --global user.email "adres@example.com"

# Inicjalizuje lokalne repozytorium (-b main: tworzy domyślną gałąź o nazwie main)
git init -b main

# Wyświetla status: niezleżone pliki, zmienione pliki, przygotowane do commita
git status

Dodaj pliki do poczekalni, przejrzyj zmiany i utwórz commit:

# Dodaje wszystkie pliki z bieżącego katalogu do poczekalni (staging area)
git add .

# Wyświetla różnice między wersją w poczekalni a ostatnią wersją w repozytorium
# (--staged: pokazuje tylko zmienione pliki przygotowane do commita)
git diff --staged

# Sprawdza aktualny status (powinny być zielone pliki gotowe do commita)
git status

# Zapisuje przygotowane zmiany z wiadomością komentarza
# (-m: wiadomość commita, "feat: add...": konwencja opisywania zmian)
git commit -m "feat: add Hello World console app"

# Wyświetla historię commitów w skróconej formie (--oneline: jeden commit w jednym wierszu)
git log --oneline

Połącz lokalne repozytorium z adresem skopiowanym z GitHuba i wyślij gałąź main:

# Tworzy odnośnik do zdalnego repozytorium o nazwie "origin" 
# (origin: konwencja dla głównego repozytorium na serwerze)
git remote add origin https://github.com/USERNAME/REPOSITORY.git

# Wyświetla listę zdanych repozytoriów z ich adresami URL
# (-v: verbose, pokazuje zarówno fetch jak i push URL)
git remote -v

# Publikuje lokalną gałąź main na serwer (zdalny branch origin/main)
# (-u: ustawia tracking, czyli powiązuje lokalną gałąź z gałęzią zdalną)
git push -u origin main

Zamień USERNAME i REPOSITORY na wartości z adresu repozytorium. Odśwież stronę GitHuba: powinny być widoczne pliki i commit.

    ✓
  • Opcja -u ustawia śledzenie gałęzi zdalnej
  • Przy kolejnych wysyłkach z tej gałęzi wystarczy git push

06

GIT / FETCH I PULL

Odbierz zmianę z GitHuba

Teraz pobrania zmianę, którą przed chwilą dodałeś na GitHubie do swojego komputera.

fetch pobiera informacje o zdalnych commitach, ale nie zmienia bieżących plików:

# Pobiera informacje o zmianach ze zdalnego repozytorium (origin)
# Nie zmienia lokalnych plików, tylko aktualizuje referencje do gałęzi zdalnej
git fetch origin

# Pokazuje aktualny status lokalnego repozytorium
git status

# Wyświetla historię commitów z dodatkowymi informacjami
# (--all: pokazuje commity ze wszystkich gałęzi, lokalnych i zdalnych)
# (--decorate: pokazuje gałęzie i tagi)
# (-5: wyświetla tylko ostatnie 5 commitów)
git log --oneline --all --decorate -5

# Porównuje różnice między HEAD (aktualnym lokalnym commitem) a origin/main (zdalnym committem)
# Pokazuje jakie zmiany są na serwerze, których brakuje lokalnie
git diff HEAD..origin/main

Teraz zintegruj pobraną zmianę z lokalną gałęzią:

# Pobiera zmiany ze zdalnego repozytorium i integruje je z lokalną gałęzią
# (--ff-only: fast-forward only, integracza powiedzie się tylko jeśli jest to fast-forward,
#  czyli brak konfliktów - jeśli byłyby konflikty, komenda się przerywa)
git pull --ff-only origin main

# Sprawdza status po pull (powinien pokazać brak zmian, wszystko jest synchronizowane)
git status
    ✓
  • Po fetch README nie pojawi się jeszcze w katalogu
  • Po pull jest już lokalnie
  • Opcja --ff-only przerwie operację, jeśli integracja wymagałaby utworzenia merge commita
05

ŚCIĄGA

Komendy, które właśnie poznałeś

git status
Pokazuje gałąź oraz pliki zmienione, przygotowane i nieśledzone.
git add
Wybiera zmiany do commita; git add . dodaje zmiany z bieżącego katalogu.
git diff
Pokazuje różnice; git diff --staged sprawdza poczekalnię.
git commit
Zapisuje przygotowane zmiany jako lokalny punkt historii.
git log
Wyświetla historię commitów; --oneline skraca każdy do jednego wiersza.
git fetch
Odświeża informacje o zdalnych gałęziach, bez zmiany plików.
git pull
Pobiera zmiany i integruje je z aktualną gałęzią.
git push
Publikuje lokalne commity w zdalnym repozytorium.
git branch
Pokazuje i tworzy gałęzie; git branch --list je wyświetla.
git remote
Konfiguruje zdalne repozytorium; opcja -v pokazuje adresy.

ZADANIE DO WYKONANIA

Oddaj działające repo

Dokończ ćwiczenie samodzielnie i sprawdź każdy warunek:

  • Przeanalizowałeś strukturę plików i zrozumiałeś rolę każdego pliku.
  • Program .NET Console uruchamia się i wypisuje własny tekst powitalny.
  • Projekt otwiera się i uruchamia w VS Code oraz Riderze; potrafisz wskazać jedną różnicę.
  • Publiczne repozytorium GitHub zawiera kod, README i historię commitów.
  • Dodałeś plik README.md na GitHubie przez interfejs webowy i potwierdziłeś zmianę (commit).
  • Zmianę z GitHuba pobrałeś przez fetch, a potem zintegrowałeś przez pull.
  • Wykonałeś co najmniej dwa commity i wysłałeś zmiany przez push.
  • Końcowe git status nie pokazuje niezapisanych zmian.

07

DIAGNOSTYKA

Gdy coś nie działa

dotnet nie jest rozpoznawane

Sprawdź, czy zainstalowano .NET SDK, a nie tylko runtime. Otwórz ponownie terminal po instalacji i wykonaj dotnet --info.

code nie jest rozpoznawane

Otwórz VS Code z menu Start i wybierz File → Open Folder…. CLI nie jest wymagane.

GitHub odrzuca logowanie w terminalu

Użyj logowania przez przeglądarkę oferowanego przez Git Credential Manager. Nie wpisuj hasła do GitHuba jako hasła Git i nie publikuj tokenu.

git push odrzuca wysyłkę

Wykonaj git fetch origin, sprawdź git status i historię. Nie używaj git push --force. Jeśli zdalne repo ma niezależną historię, utwórz nowe puste repo albo sklonuj zdalne i przenieś do niego pliki projektu.
