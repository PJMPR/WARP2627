01

CELE LABORATORIUM

Po spotkaniu potrafisz

  • Współpracować w jednym repozytorium i synchronizować lokalny main.
  • Tworzyć gałęzie feature/*, commity i publikować je przez push.
  • Otwierać Pull Request, komentować konkretne linie i wysyłać review.
  • Poprawiać istniejący PR kolejnym commitem, zatwierdzać i scalać zmiany.
  • Pracować równolegle na osobnych plikach i ograniczać ryzyko konfliktu.
  • Rozpoznać znaczniki konfliktu i bezpiecznie rozwiązać konflikt lokalnie.
  • Tworzyć czytelną dokumentację przy użyciu podstaw Markdown.
  • Sprawdzać gałąź, stan roboczy, historię i repozytorium zdalne.

Stanowisko i wspólne repozytorium

STUDENT A / GITHUB

Utwórz repozytorium i zaproś partnera

  1. Na GitHubie kliknij + → New repository. Wpisz student-it-knowledge-base, wybierz widoczność uzgodnioną z prowadzącym i zaznacz Add a README file. Kliknij Create repository.

02

STUDENT B / GITHUB

Zaakceptuj zaproszenie

Otwórz powiadomienie lub wiadomość e-mail od GitHuba, przejdź do zaproszenia i kliknij Accept invitation. Od tej chwili oboje jesteście collaboratorami i technicznie możecie scalać PR-y.

Zasada tego ćwiczenia

GitHub bez skonfigurowanej ochrony gałęzi nie musi wymagać recenzji. Mimo posiadanych uprawnień nie commitujcie bezpośrednio do main i nie scalajcie własnego PR-u. To reguła zespołu, nie zabezpieczenie techniczne.

WPROWADZENIE

Słownik współpracy

branch
Osobna linia pracy. Pozwala przygotować zmianę bez naruszania stabilnego main.
commit
Lokalny, nazwany zapis przygotowanego zestawu zmian — punkt w historii projektu.
push
Wysyła lokalne commity i gałąź do repozytorium na GitHubie.
pull
Pobiera zmiany ze zdalnej gałęzi i włącza je do aktualnej gałęzi lokalnej.
Pull Request
Prośba o przejrzenie i włączenie zmian z jednej gałęzi do drugiej, tutaj do main.
review
Recenzja zmian w PR: komentarze, zatwierdzenie albo formalna prośba o poprawki.
merge
Połączenie zaakceptowanej gałęzi roboczej z gałęzią docelową.
conflict
Sytuacja, w której Git nie potrafi sam wybrać między sprzecznymi zmianami; autor musi uzgodnić wynik.

Po wykonaniu wszystkich etapów repozytorium powinno mieć poniższą strukturę. Nie twórzcie od razu pustych katalogów — kolejne pliki i foldery powstaną podczas pracy na branchach.

ETAP 1

UKOS — Student A tworzy, Student B recenzuje

STUDENT A / AUTOR

feature/bash-cheatsheet

Tworzy docs/ukos/bash.md, publikuje branch, otwiera PR i odpowiada na review.

STUDENT B / RECENZENT

Review i merge

Komentuje konkretną linię, prosi o poprawkę, potem zatwierdza i scala PR.

01

STUDENT A / BRANCH MAIN → FEATURE

Zsynchronizuj, utwórz branch i dokument

Najpierw przejdź na main. pull --ff-only pobiera aktualny stan i zatrzyma się zamiast tworzyć nieoczekiwany merge. Dopiero potem utwórz gałąź roboczą.

git switch main
git pull --ff-only origin main
git switch -c feature/bash-cheatsheet
git status

W VS Code utwórz docs/ukos/bash.md. Dla każdego polecenia pwd, ls, cd, mkdir, touch, cp, mv, rm, cat i clear dodaj opis oraz przykład. Użyj nagłówków, tabeli lub listy i bloków bash.

GAŁĄŹ: feature/bash-cheatsheet

git status
git add docs/ukos/bash.md
git commit -m "docs: add bash cheatsheet"
git push -u origin feature/bash-cheatsheet
git log --oneline -3
    ✓
  • status po commicie jest czysty; log pokazuje docs: add bash cheatsheet.
  • Na GitHubie istnieje branch feature/bash-cheatsheet z nowym plikiem.
02

STUDENT A / GITHUB

Otwórz Pull Request do main

  1. Kliknij Compare & pull request (lub Pull requests → New pull request).
  2. Ustaw base: main i compare: feature/bash-cheatsheet.
  3. Tytuł: docs: add Bash cheatsheet. W opisie napisz, co dodano i jak sprawdzono linki/formatowanie.
  4. Kliknij Create pull request. Nie scalaj własnej zmiany.
03

STUDENT B / GITHUB

Wykonaj Code Review

  1. Otwórz PR i kartę Files changed.
  2. Najedź na konkretną linię, kliknij niebieski + i dodaj rzeczowy komentarz, np. „Dodaj ostrzeżenie, że rm usuwa pliki bez kosza”. Wybierz Start a review.
  3. Kliknij Review changes, wybierz Request changes, podsumuj oczekiwaną poprawkę i wyślij review.
OpcjaZnaczenieKiedy użyć
CommentUwagi bez decyzji.Pytanie lub sugestia, która nie blokuje akceptacji.
Request changesFormalna prośba o poprawki.Zmiana powinna zostać poprawiona przed merge.
ApproveZatwierdzenie zmian.Po sprawdzeniu poprawionej wersji.

STUDENT A → STUDENT B

Popraw ten sam PR, zatwierdź i scal

Student A pozostaje na feature/bash-cheatsheet, poprawia plik, a następnie wykonuje kolejny commit i zwykły push. GitHub automatycznie doda commit do już otwartego PR-u.

git status
git add docs/ukos/bash.md
git commit -m "docs: clarify rm command"
git push
git log --oneline -3

Student B ponownie sprawdza Files changed, wybiera Review changes → Approve, a potem Merge pull request → Confirm merge. Może usunąć zdalny branch przyciskiem Delete branch.

    ✓
  • PR jest oznaczony jako Merged, a docs/ukos/bash.md znajduje się na main.

03

WZAJEMNE REVIEW

Recenzujcie na krzyż i scalcie kolejno

  1. Student A recenzuje PR feature/readme Studenta B.
  2. Student B recenzuje PR feature/dotnet-cli Studenta A.
  3. Każdy autor wprowadza ewentualną poprawkę na swoim branchu, robi commit i git push.
  4. Po zatwierdzeniu scalcie najpierw jeden, a potem drugi PR.
  5. Na obu komputerach wykonajcie synchronizację poniżej.
git switch main
git pull --ff-only origin main
git status
git log --oneline -6
Dlaczego to zwykle nie powoduje konfliktu?

Git najłatwiej łączy zmiany dotyczące różnych plików lub różnych linii. Student A tworzy plik PRG1, a Student B zmienia README, więc zmiany się nie nakładają. Konflikt nadal jest możliwy, jeśli obie osoby zmienią ten sam fragment.

    ✓
  • main zawiera README.md oraz dokumenty bash.md, git.md i dotnet-cli.md.
  • Linki z README otwierają wszystkie trzy dokumenty.

ETAP 4 · BONUS

Kontrolowany konflikt w README

Zakres

Konflikt dotyczy wyłącznie dokumentacji studentów, nie plików strony WARP. Nie używajcie git push --force, git reset --hard ani innych destrukcyjnych skrótów.

01

OBOJE / TEN SAM PUNKT STARTOWY

Utwórzcie dwie gałęzie z aktualnego main

Każda osoba wykonuje na swoim komputerze pierwsze trzy polecenia. Następnie Student A tworzy feature/readme-purpose-a, a Student B — feature/readme-purpose-b.

git switch main
git pull --ff-only origin main
git status

# Student A:
git switch -c feature/readme-purpose-a

# Student B (na swoim komputerze):
git switch -c feature/readme-purpose-b

Oboje zmieniają dokładnie tę samą linię opisu celu w README.md, ale wpisują różne zdania. Każdy zapisuje i publikuje swoją zmianę.

git add README.md
git commit -m "docs: refine knowledge base purpose"
git push -u origin NAZWA-WŁASNEJ-GAŁĘZI

Utwórzcie dwa PR-y do main. Zrecenzujcie i scalcie PR Studenta A. PR Studenta B pozostaje otwarty i GitHub powinien zgłosić konflikt.

02

STUDENT B / OBSŁUGIWANY PR: PURPOSE-B

Scal aktualny main do gałęzi roboczej

Teraz obsługujecie drugi, nadal otwarty PR: feature/readme-purpose-b → main. Student B pozostaje autorem tej gałęzi. Pobiera nowe dane i scala aktualny zdalny main do swojej gałęzi:

git switch feature/readme-purpose-b
git status
git fetch origin
git merge origin/main

fetch aktualizuje informacje o GitHubie bez zmiany plików. merge origin/main próbuje włączyć już scalony PR Studenta A do aktualnej gałęzi Studenta B. Git zatrzyma operację na konflikcie i zapisze w README.md znaczniki:

<<<<<<< HEAD
Wersja celu ze Studenta B.
=======
Wersja celu już scalona od Studenta A.
>>>>>>> origin/main
03

STUDENT B / ROZWIĄZANIE

Uzgodnij treść i dokończ merge

  1. Uruchom git status — plik będzie oznaczony jako both modified.
  2. Wspólnie wybierzcie lub zredagujcie docelową treść. Usuńcie wszystkie linie <<<<<<<, ======= i >>>>>>>.
  3. Zapiszcie plik, sprawdźcie podgląd Markdown i wyszukajcie, czy nie pozostały znaczniki.
git status
git add README.md
git commit -m "docs: resolve README purpose conflict"
git push
git log --oneline -5

Push aktualizuje ten sam drugi PR. Student A ponownie sprawdza Files changed, zatwierdza i scala PR Studenta B. Na koniec oboje przechodzą na main i wykonują git pull --ff-only origin main.

    ✓
  • Drugi PR nie ma konfliktu, zawiera uzgodniony opis i może zostać scalony.
  • W README.md nie ma znaczników konfliktu.

10

DIAGNOSTYKA

Najczęstsze problemy

git pull --ff-only odmawia wykonania

Sprawdź git status. Prawdopodobnie jesteś na złej gałęzi, masz niezapisane zmiany albo lokalny main zawiera własne commity. Nie resetuj historii. Zabezpiecz pracę na osobnym branchu i poproś prowadzącego o sprawdzenie.

Commit trafił bezpośrednio na main

Nie wysyłaj go od razu. Utwórz branch wskazujący ten commit (git switch -c feature/nazwa) i poproś prowadzącego o pomoc w bezpiecznym przywróceniu lokalnego main. Nie używaj reset --hard.

GitHub nie pokazuje przycisku Compare & pull request

Wejdź w Pull requests → New pull request i ręcznie wybierz base: main oraz swój branch jako compare. Sprawdź też, czy wykonano git push -u origin ....

Opcja Request changes jest niedostępna

W niektórych konfiguracjach GitHub ogranicza formalne żądanie zmian. Dodaj komentarz do linii i podsumowanie review, a autor niech potraktuje je jako wymaganą poprawkę zgodnie z zasadami ćwiczenia.

Push został odrzucony albo pyta o logowanie

Sprawdź git remote -v, dostęp do Internetu i zaakceptowanie zaproszenia. Dla HTTPS zaloguj się w oknie Git Credential Manager; nie wpisuj hasła do konta jako hasła Git i nie udostępniaj tokenów.

Po merge lokalnie nie widać plików partnera

Merge na GitHubie nie aktualizuje automatycznie komputera. Wykonaj git switch main, potem git pull --ff-only origin main i sprawdź git log --oneline.

W README zostały znaczniki konfliktu

Wyszukaj <<<<<<<, ======= i >>>>>>>. Uzgodnij jedną treść, usuń wszystkie znaczniki, sprawdź podgląd Markdown, a dopiero potem wykonaj git add i commit.

Link względny zwraca 404

Sprawdź wielkość liter i ścieżkę. Z głównego README poprawne przykłady to docs/ukos/bash.md, docs/warp/git.md i docs/prg1/dotnet-cli.md.
