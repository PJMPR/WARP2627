LABORATORIUM 07 / LIVE CODING

Pierwszy workflow
GitHub Actions

Student wykonuje laboratorium krok po kroku razem z prowadzącym. Wspólnie zautomatyzujemy budowanie i uruchamianie projektu .NET 10: najpierw ręcznie, potem po pushu, a na końcu przy Pull Requeście.

PLIKYAMLPIPELINEBUILD / RUN
00

TRYB ZAJĘĆ / LIVE CODING

Pracujemy razem z prowadzącym

To laboratorium nie jest zadaniem do samodzielnego przeczytania i wykonania we własnym tempie. Prowadzący tworzy workflow na ekranie, a każdy student równolegle powtarza te same zmiany we własnym repozytorium.

  1. Najpierw omawiamy. Przed dodaniem fragmentu wspólnie ustalamy, do czego służy i gdzie powinien znaleźć się w YAML.
  2. Potem zapisujemy. Prowadzący i studenci dodają ten sam mały fragment konfiguracji.
  3. Uruchamiamy. Wykonujemy commit i push, a następnie obserwujemy workflow w zakładce Actions.
  4. Porównujemy logi. Zatrzymujemy się przy nowym stepie i sprawdzamy jego wejście, wynik oraz kod zakończenia.
  5. Wspólnie diagnozujemy. Jeżeli wynik studenta różni się od wyniku prowadzącego, nie przechodzimy dalej, tylko szukamy różnicy w ścieżce, wcięciach lub konfiguracji.
  6. Dopiero potem rozwijamy workflow. Następny step dodajemy, gdy bieżąca wersja działa u wszystkich.
Nie kopiuj gotowego pliku

Pełna wersja YAML znajduje się na końcu wyłącznie do porównania. Podczas zajęć student buduje plik razem z prowadzącym, jeden fragment na raz.

01

CELE LABORATORIUM

Po spotkaniu potrafisz

  • Wyjaśnić, czym są workflow, event, job, step, runner i action.
  • Rozpoznać strukturę pliku YAML i poprawnie stosować wcięcia.
  • Utworzyć workflow w katalogu .github/workflows.
  • Przygotować środowisko .NET na runnerze GitHub.
  • Uruchomić polecenia Bash budujące i uruchamiające projekt z pliku .csproj.
  • Stopniowo skonfigurować triggery workflow_dispatch, push i pull_request.
  • Odczytać logi workflow i znaleźć krok, który zakończył się błędem.
  • Zablokować merge Pull Requesta, dopóki wymagany build nie zakończy się sukcesem.
Zakres laboratorium

Nie tworzymy solution .sln, nie uruchamiamy testów i nie wdrażamy aplikacji. Workflow pracuje z jednym istniejącym projektem .csproj.

02

PUNKT STARTOWY

Przygotuj działający projekt

Skorzystaj z projektu .NET z poprzednich laboratoriów. Projekt musi korzystać z net10.0, zawierać plik .csproj, budować się lokalnie i kończyć działanie po uruchomieniu. Najwygodniejsza będzie aplikacja konsolowa.

LOCAL

KONTROLA PRZED AUTOMATYZACJĄ

Sprawdź projekt na swoim komputerze

W terminalu Bash przejdź do katalogu repozytorium. Zastąp przykładową ścieżkę rzeczywistym położeniem swojego pliku projektu.

find . -name "*.csproj"

PROJECT_PATH="./src/MyApp/MyApp.csproj"
dotnet restore "$PROJECT_PATH"
dotnet build "$PROJECT_PATH" --configuration Release --no-restore
dotnet run --project "$PROJECT_PATH" --configuration Release --no-build
    ✓
  • find pokazuje plik projektu, którego chcesz użyć.
  • dotnet build kończy się komunikatem Build succeeded.
  • dotnet run wypisuje wynik programu i sam się kończy.
Dlaczego cudzysłowy?

Zapis "$PROJECT_PATH" chroni ścieżkę zawierającą spacje. To dobra praktyka w skryptach Bash.

03

WPROWADZENIE

Jak działa GitHub Actions

PojęcieZnaczeniePrzykład w tym laboratorium
WorkflowCała automatyzacja opisana w jednym pliku YAML..github/workflows/build.yml
Event / triggerZdarzenie rozpoczynające workflow.Ręczne kliknięcie, push albo Pull Request.
JobZestaw kroków wykonywany na jednym runnerze.build

GitHub tworzy czysty runner dla każdego uruchomienia. Dlatego workflow musi pobrać repozytorium, zainstalować właściwą wersję .NET, odtworzyć zależności, zbudować projekt i dopiero potem go uruchomić.

04

YAML

Struktura pliku workflow

YAML opisuje dane za pomocą kluczy, wartości i list. Poziom zagnieżdżenia wyznaczają spacje. W tym pliku używamy dwóch spacji na poziom i nie używamy tabulatorów.

name: Build .NET project       # klucz i wartość

on:                            # obiekt zagnieżdżony
  workflow_dispatch:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:                     # lista
      - name: Checkout repository
        uses: actions/checkout@v4
      - name: Show directory
        run: pwd
SkładniaZnaczenieUwaga
klucz: wartośćPojedyncza właściwość.Po dwukropku występuje spacja.
klucz: i wcięcieZagnieżdżony obiekt.Dzieci mają większe wcięcie.
- elementElement listy.Każdy step zaczyna się myślnikiem.
|Wielowierszowy tekst.Przydatny dla kilku poleceń Bash.
# komentarzOpis ignorowany przez parser.Komentarze wyjaśniają intencję.
Uwaga na klucz on

on określa zdarzenia uruchamiające workflow. Edytor może traktować to słowo jak wartość logiczną, jeżeli używa starego parsera YAML. GitHub Actions rozpoznaje je poprawnie jako klucz.

05

ETAP 1 / RĘCZNIE

Uruchom workflow przyciskiem

Najpierw użyjemy wyłącznie workflow_dispatch. Workflow zbudujemy krok po kroku. Po każdym rozszerzeniu pliku wykonaj commit, push i ręczne uruchomienie. Nie dodawaj kolejnego stepu, dopóki bieżąca wersja nie zakończy się sukcesem.

01

SZKIELET

Utwórz pierwszy działający workflow

Utwórz katalog .github/workflows, a w nim plik build.yml. Na razie workflow tylko potwierdzi uruchomienie runnera.

name: Build .NET project

on:
  workflow_dispatch:

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - name: Confirm runner
        shell: bash
        run: echo "Runner is ready"

name nadaje nazwę workflow. workflow_dispatch pozwala uruchomić go przyciskiem. jobs zawiera job build, wykonywany na świeżej maszynie Ubuntu. Lista steps ma na razie jedno polecenie Bash.

git switch main
git pull --ff-only origin main
git add .github/workflows/build.yml
git commit -m "ci: add workflow skeleton"
git push origin main
Dlaczego najpierw main?

GitHub udostępnia ręczne uruchamianie przez workflow_dispatch dopiero wtedy, gdy plik workflow istnieje na domyślnej gałęzi repozytorium. Na tym etapie main nie jest jeszcze chroniony — ochronę włączysz po przygotowaniu kontroli PR.

RUN

PO KAŻDEJ ZMIANIE

Zapisz, uruchom i przeczytaj logi

  1. Po każdej zmianie wykonaj git add, git commit i git push origin main.
  2. Otwórz repozytorium na GitHubie i przejdź do zakładki Actions.
  3. Z lewej strony wybierz workflow Build .NET project.
  4. Kliknij Run workflow, wybierz branch main i ponownie kliknij Run workflow.
  5. Otwórz nowe uruchomienie, a następnie job build.
  6. Rozwiń nowo dodany step i sprawdź jego log. Zielony znacznik oznacza kod wyjścia 0.

W kolejnych punktach pokazane są tylko fragmenty, które należy dopisać do rosnącego pliku. Nie usuwaj wcześniej dodanych stepów.

02

CHECKOUT

Pobierz kod repozytorium

Dodaj nowy element na końcu listy steps:

      - name: Checkout repository
        uses: actions/checkout@v4

Runner jest pustą maszyną — samo uruchomienie workflow nie kopiuje na nią repozytorium. Gotowa akcja actions/checkout pobiera właściwy commit i ustawia go jako bieżący katalog. uses oznacza użycie gotowej akcji zamiast własnego polecenia.

git add .github/workflows/build.yml
git commit -m "ci: checkout repository"
git push origin main

Uruchom workflow ręcznie. W logu kroku Checkout repository znajdź informację o pobranym repozytorium i commicie.

03

SETUP

Wybierz wersję .NET

Nad sekcją jobs dodaj zmienną z wersją SDK. W tym laboratorium projekt korzysta z net10.0, dlatego konfigurujemy .NET SDK 10.

env:
  DOTNET_VERSION: 10.0.x

Na końcu listy steps dopisz:

      - name: Setup .NET
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: ${{ env.DOTNET_VERSION }}

actions/setup-dotnet udostępnia wybrane SDK w zmiennej PATH. Sekcja with przekazuje parametry do akcji, a zapis ${{ env.DOTNET_VERSION }} odczytuje zmienną w składni GitHub Actions.

git add .github/workflows/build.yml
git commit -m "ci: configure dotnet sdk"
git push origin main

Uruchom workflow ręcznie i sprawdź, czy krok Setup .NET pokazuje oczekiwaną wersję SDK.

04

RESTORE

Odtwórz zależności projektu

W istniejącej sekcji env dopisz ścieżkę do swojego projektu:

  PROJECT_PATH: ./src/MyApp/MyApp.csproj

Na końcu listy steps dodaj:

      - name: Restore dependencies
        shell: bash
        run: dotnet restore "$PROJECT_PATH"

dotnet restore czyta wskazany .csproj i pobiera wymagane pakiety. shell: bash jawnie wybiera powłokę, a "$PROJECT_PATH" odczytuje zmienną środowiskową i bezpiecznie obsługuje spacje w ścieżce.

git add .github/workflows/build.yml
git commit -m "ci: restore project dependencies"
git push origin main

Uruchom workflow ręcznie. Jeżeli step nie znajduje projektu, porównaj wartość PROJECT_PATH z wynikiem find . -name "*.csproj".

05

BUILD

Zbuduj projekt w konfiguracji Release

Na końcu listy steps dodaj:

      - name: Build project
        shell: bash
        run: dotnet build "$PROJECT_PATH" --configuration Release --no-restore

--configuration Release wybiera konfigurację przeznaczoną do gotowego programu. --no-restore zapobiega powtórnemu pobieraniu zależności — restore został wykonany w poprzednim stepie. Jeśli kompilator zwróci błąd, job zatrzyma się i następny step nie zostanie wykonany.

git add .github/workflows/build.yml
git commit -m "ci: build dotnet project"
git push origin main

Uruchom workflow ręcznie. Rozwiń Build project i znajdź komunikat Build succeeded.

06

RUN

Uruchom zbudowany program

Na końcu listy steps dodaj ostatni krok:

      - name: Run project
        shell: bash
        run: dotnet run --project "$PROJECT_PATH" --configuration Release --no-build

--project wskazuje konkretny .csproj. --no-build uruchamia pliki utworzone przez poprzedni step, zamiast ponownie kompilować projekt. Wynik programu pojawi się bezpośrednio w logu.

git add .github/workflows/build.yml
git commit -m "ci: run built project"
git push origin main

Uruchom workflow ręcznie. Znajdź wynik aplikacji w kroku Run project.

    ✓
  • Workflow ma sześć widocznych stepów, łącznie z krokiem kontrolnym.
  • Build project zawiera komunikat Build succeeded.
  • Run project pokazuje wynik programu i kończy się sukcesem.
  • Dopiero teraz przejdź do etapu 2.
06

ETAP 2 / PUSH

Uruchamiaj workflow po wysłaniu zmian

Zachowaj możliwość ręcznego uruchomienia i dodaj drugi trigger. Od tej chwili każdy push do brancha main uruchomi workflow automatycznie.

ON

ZMIEŃ TYLKO TRIGGER

Dodaj zdarzenie push

W pliku build.yml zastąp dotychczasową sekcję on poniższą konfiguracją. Pozostała część pliku nie zmienia się.

on:
  workflow_dispatch:
  push:
    branches:
      - main
git add .github/workflows/build.yml
git commit -m "ci: run build on push"
git push

Sam git push powinien teraz utworzyć nowe uruchomienie w zakładce Actions. Nie klikaj przycisku Run workflow.

    ✓
  • Nowe uruchomienie ma zdarzenie push.
  • Workflow zakończył się sukcesem bez ręcznego startu.
  • Dopiero po tym wyniku przejdź do etapu 3.
07

ETAP 3 / PULL REQUEST

Sprawdzaj kod przed scaleniem

Ostatnia wersja uruchomi workflow dla zmian wysyłanych do main oraz dla Pull Requestów skierowanych do main. Branch roboczy nie musi mieć konkretnej nazwy.

PR

DOCELOWY TRIGGER

Dodaj pull_request

Utwórz branch roboczy, a następnie zastąp sekcję on wersją docelową:

git switch -c ci/github-actions
on:
  workflow_dispatch:
  push:
    branches:
      - main
  pull_request:
    branches:
      - main
git add .github/workflows/build.yml
git commit -m "ci: validate pull requests to main"
git push
  1. Na GitHubie otwórz Pull Request z ci/github-actions do main.
  2. Przejdź do zakładki Checks albo sekcji kontroli na dole zakładki Conversation.
  3. Otwórz szczegóły kontroli build i sprawdź logi.
  4. Nie scalaj PR-a, dopóki kontrola jest w toku albo zakończyła się błędem.
    ✓
  • Otwarcie PR-a uruchamia workflow ze zdarzeniem pull_request.
  • PR pokazuje zieloną kontrolę build.
  • Po kolejnym pushu do brancha PR-a kontrola uruchamia się ponownie.
08

OCHRONA MAIN

Zablokuj merge po nieudanym buildzie

Sama kontrola informuje o błędzie, ale bez reguły repozytorium nadal można ją zignorować. Właściciel repozytorium powinien wymagać pomyślnego statusu build.

  1. Upewnij się, że workflow dla PR-a wykonał się przynajmniej raz — dopiero wtedy status build pojawi się na liście.
  2. Przejdź do Settings → Rules → Rulesets i wybierz New ruleset → New branch ruleset.
  3. Nazwij regułę Protect main, ustaw ją jako aktywną i w Target branches wskaż branch main.
  4. Włącz Require a pull request before merging.
  5. Włącz Require status checks to pass i dodaj kontrolę build.
  6. Jeżeli opcja jest dostępna, włącz wymaganie aktualnego brancha przed scaleniem.
  7. Zapisz ruleset.
Nazwa wymaganej kontroli

Build .NET project to nazwa całego workflow, a build to identyfikator joba i nazwa kontroli wymagana przy merge. Nie zmieniaj identyfikatora joba po skonfigurowaniu reguły.

FAIL

KONTROLOWANA PRÓBA

Sprawdź, czy ochrona naprawdę działa

Na branchu PR-a wprowadź tymczasowy błąd kompilacji, np. usuń średnik w pliku .cs. Wykonaj commit i push, a następnie obserwuj PR.

git add .
git commit -m "test: verify failed build blocks merge"
git push

GitHub powinien pokazać czerwoną kontrolę i zablokować merge. Następnie napraw błąd, wykonaj kolejny commit oraz push. Nie wyłączaj reguły i nie scalaj zepsutej wersji.

git add .
git commit -m "fix: restore successful build"
git push
    ✓
  • Nieudany build blokuje merge.
  • Po naprawie nowa kontrola kończy się sukcesem.
  • Przycisk merge staje się dostępny dopiero po zielonym statusie.

REF

PLIK DO PORÓWNANIA

Sprawdź końcową wersję build.yml

Dopiero po wykonaniu wszystkich etapów razem z prowadzącym porównaj swój plik z poniższą wersją. Nie kopiuj jej wcześniej — celem ćwiczenia jest wspólne zbudowanie workflow i sprawdzenie każdego przyrostu.

name: Build .NET project

on:
  workflow_dispatch:
  push:
    branches:
      - main
  pull_request:
    branches:
      - main

env:
  DOTNET_VERSION: 10.0.x
  PROJECT_PATH: ./src/MyApp/MyApp.csproj

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - name: Confirm runner
        shell: bash
        run: echo "Runner is ready"

      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Setup .NET
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: ${{ env.DOTNET_VERSION }}

      - name: Restore dependencies
        shell: bash
        run: dotnet restore "$PROJECT_PATH"

      - name: Build project
        shell: bash
        run: dotnet build "$PROJECT_PATH" --configuration Release --no-restore

      - name: Run project
        shell: bash
        run: dotnet run --project "$PROJECT_PATH" --configuration Release --no-build

Różnić powinny się tylko wartości zależne od projektu, przede wszystkim DOTNET_VERSION i PROJECT_PATH. Nazwy stepów mogą być inne, ale ich kolejność i działanie powinny pozostać takie same.

10

DIAGNOSTYKA

Najczęstsze problemy

Nie widzę przycisku Run workflow

Sprawdź, czy plik istnieje na domyślnej gałęzi main, zawiera workflow_dispatch i znajduje się w katalogu .github/workflows. Wybierz właściwy workflow z listy po lewej stronie zakładki Actions.

Workflow nie znajduje pliku .csproj

Runner zaczyna pracę w katalogu głównym repozytorium. Porównaj PROJECT_PATH z wynikiem lokalnego find . -name "*.csproj". Wielkość liter ma znaczenie na runnerze Linux.

Wersja .NET nie pasuje do projektu

Otwórz .csproj i sprawdź TargetFramework. W tym laboratorium oczekujemy net10.0, a workflow powinien zawierać DOTNET_VERSION: 10.0.x. Jeżeli projekt używa starszego frameworka, zaktualizuj go wspólnie z prowadzącym przed kontynuowaniem.

Krok Run project nigdy się nie kończy

Workflow zakłada aplikację konsolową, która kończy działanie. Serwer WWW lub program czekający na dane użytkownika będzie działał bez końca. Użyj projektu konsolowego i usuń oczekiwanie na Console.ReadLine().

Workflow nie uruchamia się po pushu

Sprawdź filtr branches. W etapie 2 push musi trafić do main. W wersji docelowej push nadal uruchamia workflow na main, a branche robocze są sprawdzane przez pull_request.

Status build nie pojawia się w Rulesets

Najpierw otwórz PR i poczekaj, aż job build wykona się przynajmniej raz. Następnie odśwież ustawienia rulesetu.

YAML zgłasza błąd składni

Sprawdź wcięcia, brak tabulatorów i dwukropki. Otwórz uruchomienie w Actions — GitHub zwykle wskazuje linię, której nie potrafi odczytać.
