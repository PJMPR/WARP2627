00

BRIEF / ZADANIE

Samodzielnie ulepsz istniejący pipeline

Pracujesz na własnym repozytorium i workflow przygotowanym podczas laboratorium 07. Nie tworzysz automatyzacji od zera. Twoim zadaniem jest przeanalizować istniejący plik, dodać nowe kontrole oraz wykazać na podstawie logów, że potrafisz zdiagnozować nieudane uruchomienie.

  1. Pracuj na branchu. Wszystkie zmiany wykonaj poza main.
  2. Rozwijaj małymi krokami. Po każdej istotnej zmianie wykonaj osobny commit i push.
  3. Obserwuj Actions. Każdy push do brancha otwartego Pull Requesta powinien uruchomić kontrolę.
  4. Zachowaj historię próby. Nie usuwaj nieudanego uruchomienia ani commitów z kontrolowanym błędem i jego naprawą.
  5. Oddaj Pull Request. PR ma zawierać działający workflow, opis diagnostyki i dokumentację w README.
Nie pracuj bezpośrednio na main

Kontrolowany błąd ma pojawić się wyłącznie na branchu roboczym. Nie wyłączaj ochrony brancha i nie scalaj wersji z czerwoną kontrolą.

01

CELE LABORATORIUM

Po wykonaniu zadania potrafisz

  • przeczytać istniejący workflow i wskazać jego triggery, joby oraz stepy,
  • uruchamiać kontrolę dla push do main i Pull Requesta do main,
  • dodać krok wykonujący własny skrypt Bash,
  • przerwać job czytelnym komunikatem i kodem wyjścia różnym od zera,
  • odnaleźć w logach pierwszy krok, który zakończył się błędem,
  • opublikować wynik kompilacji jako artefakt uruchomienia,
  • opisać automatyczne kontrole w dokumentacji projektu.
02

PUNKT STARTOWY

Sprawdź stan repozytorium

Przed zmianami upewnij się, że projekt buduje się lokalnie, a workflow z laboratorium 07 jest zielony. Poniższe polecenia wykonaj w PowerShellu. Nazwy i ścieżki są przykładowe — dopasuj je do własnego repozytorium.

git switch main
git pull --ff-only origin main
git status

Get-ChildItem -Recurse -Filter *.csproj
dotnet build "./src/MyApp/MyApp.csproj" --configuration Release
    ✓
  • git status nie pokazuje lokalnych zmian.
  • Znasz dokładną ścieżkę do używanego pliku .csproj.
  • Lokalny build kończy się komunikatem Build succeeded.
  • Ostatnie uruchomienie workflow z laboratorium 07 jest zielone.
Najpierw napraw punkt startowy

Jeżeli istniejący workflow nie działa, nie dodawaj kolejnych kroków. Porównaj PROJECT_PATH, wersję .NET i log pierwszego nieudanego stepu z materiałem laboratorium 07.

03

BRANCH / PULL REQUEST

Przygotuj miejsce pracy

git switch -c ci/lab08-workflow
git push -u origin ci/lab08-workflow

Na GitHubie otwórz Draft Pull Request z ci/lab08-workflow do main. Dzięki temu każdy kolejny push będzie od razu widoczny jako kontrola PR-a, a opis możesz uzupełniać w trakcie pracy.

Sprawdź, czy sekcja on istniejącego workflow zawiera oba wymagane zdarzenia:

on:
  push:
    branches:
      - main
  pull_request:
    branches:
      - main
Co uruchamia workflow na branchu?

Filtr push: main nie reaguje na push do brancha roboczego. Taką zmianę sprawdza zdarzenie pull_request, gdy branch ma otwarty PR do main.

04

WINDOWS / WSL

Przygotuj terminal Ubuntu

Pracujesz na własnym komputerze bez WSL?

Zanim przejdziesz dalej, wykonaj osobną instrukcję Instalacja WSL i Ubuntu na komputerze domowym →. Wróć do tego miejsca, gdy polecenie wsl --list --verbose pokaże zainstalowane Ubuntu.

Skrypt napiszemy i uruchomimy w Bashu dostępnym przez WSL. Na komputerze może być już widoczna dystrybucja rancher-desktop, ale jest ona technicznym środowiskiem Rancher Desktop, a nie systemem przeznaczonym do pracy studenta. Zainstaluj Ubuntu i ustaw je jako domyślną dystrybucję.

01

POWERSHELL

Sprawdź zainstalowane dystrybucje

Otwórz Windows Terminal albo PowerShell. Poniższych poleceń nie wpisuj jeszcze w terminalu Linux.

wsl --list --verbose
wsl --list --online

Pierwsze polecenie pokazuje dystrybucje już zainstalowane. Gwiazdka * oznacza dystrybucję domyślną. Drugie pokazuje systemy dostępne do instalacji.

Nie usuwaj Rancher Desktop

Nie wykonuj wsl --unregister dla dystrybucji rancher-desktop ani rancher-desktop-data. Wystarczy, że Ubuntu zostanie ustawione jako domyślne.

02

INSTALACJA

Zainstaluj Ubuntu

W tym samym oknie PowerShell uruchom:

wsl --install -d Ubuntu

Jeżeli Ubuntu jest już zainstalowane, WSL wyświetli odpowiedni komunikat — wtedy przejdź do następnego kroku. Podczas pierwszego uruchomienia system poprosi o utworzenie nazwy użytkownika i hasła Linuksa. Wpisywane hasło nie jest widoczne na ekranie; to prawidłowe zachowanie.

Może być wymagany restart

Jeżeli Windows poprosi o ponowne uruchomienie komputera, wykonaj restart, ponownie otwórz PowerShell i uruchom wsl -d Ubuntu, aby dokończyć konfigurację użytkownika.

03

DOMYŚLNA DYSTRYBUCJA

Wybierz Ubuntu zamiast Rancher Desktop

Po zakończeniu instalacji wróć do PowerShella. Jeśli znajdujesz się w Ubuntu, wpisz najpierw exit. Następnie wykonaj:

wsl --set-default Ubuntu
wsl --list --verbose

Na liście gwiazdka * powinna znajdować się przy Ubuntu. Od tej chwili samo polecenie wsl uruchomi właśnie tę dystrybucję.

Jeżeli na liście widzisz inną dokładną nazwę, na przykład Ubuntu-24.04, użyj jej zamiast Ubuntu:

wsl --set-default Ubuntu-24.04

Sprawdź środowisko już w terminalu Linux:

whoami

pwd
git --version
bash --version
    ✓

  • pwd wskazuje katalog repozytorium, zwykle pod /mnt/c/....
  • Polecenia git i bash wyświetlają numery wersji.
Dwa rodzaje poleceń

Pełną listę poleceń znajdziesz w oficjalnej dokumentacji Podstawowe polecenia WSL ↗.

05

NOWA KONTROLA

Dodaj skrypt sprawdzający repozytorium

Zbudujesz skrypt scripts/check-repository.sh małymi krokami. Po każdym etapie uruchomisz go lokalnie i zobaczysz rezultat. Nie przepisuj od razu wersji końcowej — jej zadaniem jest dopiero późniejsze porównanie rozwiązania.

01

PLIK I INTERPRETER

Utwórz najprostszy skrypt

Utwórz katalog scripts, a w nim plik check-repository.sh. Dodaj dwie linie:

#!/usr/bin/env bash

echo "Starting repository check..."

Pierwsza linia to shebang. Informuje system, że plik jest skryptem Bash. Polecenie env odnajduje interpreter bash dostępny w danym środowisku. echo wypisuje tekst w terminalu.

Komentarze a shebang

Zwykła linia zaczynająca się od # jest komentarzem i Bash jej nie wykonuje. Pierwsza linia #! jest wyjątkiem — system używa jej do wyboru interpretera.

Uruchom skrypt z katalogu głównego repozytorium:

bash scripts/check-repository.sh
    ✓
  • Terminal wyświetla Starting repository check....
  • Polecenie kończy się bez błędu.
02

TRYB BEZPIECZNY

Włącz wykrywanie błędów

Pod shebangiem, przed echo, dodaj:

set -euo pipefail
OpcjaPo co jej używamy
-eZatrzymuje skrypt, gdy polecenie kończy się błędem.
-uZgłasza błąd przy próbie użycia niezdefiniowanej zmiennej.
-o pipefailWykrywa błąd dowolnego polecenia w potoku, a nie tylko ostatniego.

Te opcje pomagają szybko wykryć problem. Bez nich skrypt mógłby kontynuować pracę z błędnymi lub brakującymi danymi.

03

ARGUMENT

Odbierz ścieżkę do projektu

Usuń tymczasowe echo z pierwszego kroku. Pod set -euo pipefail dodaj zmienną i wypisz jej wartość:

PROJECT_PATH="${1:-}"

echo "Received project path: $PROJECT_PATH"

$1 oznacza pierwszy argument przekazany podczas uruchamiania skryptu. Zapis ${1:-} zwraca ten argument, a jeżeli go nie podano — pusty tekst. Wynik zostaje zapisany w zmiennej PROJECT_PATH. Cudzysłowy chronią wartości zawierające spacje.

Porównaj dwa uruchomienia:

bash scripts/check-repository.sh
bash scripts/check-repository.sh "./src/MyApp/MyApp.csproj"
    ✓
  • Za pierwszym razem po dwukropku nie ma ścieżki.
  • Za drugim razem terminal pokazuje przekazany argument.
04

PIERWSZY WARUNEK

Zatrzymaj skrypt, gdy brakuje argumentu

Zastąp ostatnią linię echo poniższym blokiem:

if [[ -z "$PROJECT_PATH" ]]; then
  echo "ERROR: Provide a project path as the first argument."
  exit 1
fi

if rozpoczyna warunek, a fi go kończy. Test -z jest prawdziwy, gdy tekst jest pusty. exit 1 natychmiast kończy skrypt kodem błędu. W GitHub Actions taki kod nada stepowi czerwony status.

Przetestuj oba przypadki ponownie. Pierwsze polecenie powinno się nie udać, a drugie przejść dalej:

bash scripts/check-repository.sh
bash scripts/check-repository.sh "./src/MyApp/MyApp.csproj"
05

PLIK PROJEKTU

Sprawdź, czy wskazany plik istnieje

Pod pierwszym blokiem if dodaj drugą kontrolę:

if [[ ! -f "$PROJECT_PATH" ]]; then
  echo "ERROR: Project file not found: $PROJECT_PATH"
  exit 1
fi

Test -f sprawdza, czy pod podaną ścieżką istnieje zwykły plik. Znak ! odwraca wynik, dlatego wnętrze warunku wykona się właśnie wtedy, gdy pliku nie znaleziono.

Najpierw podaj nieistniejącą, a następnie prawidłową ścieżkę:

bash scripts/check-repository.sh "./missing.csproj"
bash scripts/check-repository.sh "./src/MyApp/MyApp.csproj"

Zastąp przykładową ścieżkę ./src/MyApp/MyApp.csproj rzeczywistym położeniem swojego projektu.

06

README I SUKCES

Dodaj ostatnią kontrolę

Pod kontrolą projektu dodaj:

if [[ ! -s "README.md" ]]; then
  echo "ERROR: README.md is missing or empty."
  exit 1
fi

echo "Repository check passed."
echo "Project: $PROJECT_PATH"
echo "README.md is present and not empty."

Test -s sprawdza, czy plik istnieje i ma rozmiar większy od zera. Operator ! ponownie odwraca wynik. Jeżeli wszystkie warunki zostały spełnione, skrypt dociera do końcowych komunikatów. Ostatnie echo zwraca kod 0, czyli sukces, dlatego nie trzeba dopisywać exit 0.

bash scripts/check-repository.sh "./src/MyApp/MyApp.csproj"
echo $?

Specjalna zmienna $? zawiera kod zakończenia ostatniego polecenia. Po udanej kontroli powinna mieć wartość 0.

REF

WERSJA DO PORÓWNANIA

Sprawdź kompletny skrypt

Dopiero teraz porównaj swój plik z pełną wersją. Komentarze przypominają znaczenie najważniejszych instrukcji; nie musisz usuwać ich ze swojego skryptu.

#!/usr/bin/env bash
# Uruchom ten plik przy użyciu interpretera Bash.

set -euo pipefail
# Zatrzymuj wykonanie po błędach i wykrywaj brakujące zmienne.

PROJECT_PATH="${1:-}"
# Pobierz pierwszy argument lub pusty tekst, jeśli argumentu nie podano.

if [[ -z "$PROJECT_PATH" ]]; then
  # Przerwij pracę, jeżeli użytkownik nie podał ścieżki.
  echo "ERROR: Provide a project path as the first argument."
  exit 1
fi

if [[ ! -f "$PROJECT_PATH" ]]; then
  # Przerwij pracę, jeżeli wskazany plik projektu nie istnieje.
  echo "ERROR: Project file not found: $PROJECT_PATH"
  exit 1
fi

if [[ ! -s "README.md" ]]; then
  # Przerwij pracę, jeżeli README nie istnieje lub jest pusty.
  echo "ERROR: README.md is missing or empty."
  exit 1
fi

# Te linie wykonają się tylko wtedy, gdy wszystkie kontrole przejdą.
echo "Repository check passed."
echo "Project: $PROJECT_PATH"
echo "README.md is present and not empty."
07

GITHUB ACTIONS

Podłącz skrypt do workflow

W pliku workflow dodaj krok po Checkout repository, ale przed restore i build:

      - name: Check repository structure
        shell: bash
        run: bash scripts/check-repository.sh "$PROJECT_PATH"

shell: bash jawnie wybiera interpreter. Wartość $PROJECT_PATH pochodzi z sekcji env workflow i zostaje przekazana do skryptu jako pierwszy argument.

git add scripts/check-repository.sh .github/workflows/build.yml
git commit -m "ci: add repository structure check"
git push
    ✓
  • Pull Request uruchamia nowe wykonanie workflow.
  • Krok Check repository structure jest widoczny w logu.
  • Log zawiera komunikat Repository check passed.
06

KONTROLOWANY BŁĄD

Zepsuj pipeline i przeczytaj log

Teraz świadomie ustaw w PROJECT_PATH nieistniejącą ścieżkę, na przykład:

env:
  PROJECT_PATH: ./src/ProjectThatDoesNotExist/Project.csproj
git add .github/workflows/build.yml
git commit -m "test: trigger repository check failure"
git push
  1. Otwórz nieudane uruchomienie w zakładce Actions albo w kontrolach Pull Requesta.
  2. Otwórz job build i znajdź pierwszy czerwony step.
  3. Rozwiń jego log i znajdź komunikat zaczynający się od ERROR:.
  4. Zapisz w opisie PR-a nazwę stepu, komunikat błędu, przyczynę oraz plan naprawy.
  5. Sprawdź, które kolejne kroki zostały pominięte po błędzie.

W opisie Pull Requesta umieść krótką sekcję według wzoru:

## Diagnostyka kontrolowanego błędu
- Nieudany step: Check repository structure
- Komunikat: ERROR: Project file not found: ...
- Przyczyna: PROJECT_PATH wskazywał nieistniejący plik
- Naprawa: przywrócenie rzeczywistej ścieżki do .csproj
Nie używaj continue-on-error

Celem zadania jest prawidłowe zatrzymanie joba. Nie maskuj błędu przez continue-on-error: true, operator || true ani ręczne zwracanie kodu 0.

07

NAPRAWA

Przywróć zielony status

Przywróć prawidłową wartość PROJECT_PATH. W terminalu Ubuntu sprawdź skrypt:

bash scripts/check-repository.sh "./src/MyApp/MyApp.csproj"

Jeżeli .NET został skonfigurowany na Windowsie, build uruchom w PowerShellu, a nie w Ubuntu:

dotnet build "./src/MyApp/MyApp.csproj" --configuration Release

Następnie w wybranym terminalu wykonaj commit naprawy i push:

git add .github/workflows/build.yml
git commit -m "fix: restore valid project path"
git push
    ✓
  • Historia PR-a zawiera osobny commit wywołujący błąd i osobny commit z naprawą.
  • Nowe uruchomienie wykonuje kontrolę, restore i build.
  • Pull Request ponownie ma zielony status.
08

ARTEFAKT

Opublikuj wynik kompilacji

dotnet build potwierdza poprawność kodu, ale jego katalog wyjściowy zawiera również pliki tymczasowe. Dodaj po buildzie krok dotnet publish, który przygotuje uporządkowany rezultat, a następnie wyślij go jako artefakt.

      - name: Publish project
        shell: bash
        run: dotnet publish "$PROJECT_PATH" --configuration Release --no-restore --output ./artifacts/app

      - name: Upload build artifact
        uses: actions/upload-artifact@v4
        with:
          name: app-${{ github.sha }}
          path: ./artifacts/app
          if-no-files-found: error
          retention-days: 7

Krok Upload build artifact umieść po Publish project. Nazwa zawiera SHA commita, więc można jednoznacznie powiązać pobrany plik z wersją kodu.

git add .github/workflows/build.yml
git commit -m "ci: upload published application artifact"
git push
  1. Poczekaj na zielone zakończenie workflow.
  2. Otwórz stronę podsumowania uruchomienia.
  3. W sekcji Artifacts znajdź paczkę app-<sha>.
  4. Pobierz archiwum i sprawdź, czy nie jest puste.
Artefakt to nie deployment

Pliki są przechowywane przy konkretnym uruchomieniu workflow. To wynik kompilacji do pobrania, a nie opublikowana aplikacja ani GitHub Pages.

10

DIAGNOSTYKA

Najczęstsze problemy

Po wpisaniu wsl uruchamia się Rancher Desktop zamiast Ubuntu

W PowerShellu wykonaj wsl --list --verbose, odczytaj dokładną nazwę Ubuntu i ustaw ją poleceniem wsl --set-default Ubuntu. Gwiazdka na ponownie wyświetlonej liście powinna znajdować się przy Ubuntu.

Polecenie wsl --install informuje, że Ubuntu jest już zainstalowane

Nie instaluj go ponownie. Uruchom wsl -d Ubuntu, dokończ tworzenie użytkownika, wpisz exit, a następnie ustaw dystrybucję jako domyślną.

Nie pamiętam hasła albo podczas wpisywania nic się nie pojawia

Terminal Linux celowo nie pokazuje znaków hasła ani gwiazdek. Wpisz hasło i naciśnij Enter. Jest to hasło użytkownika Ubuntu, a nie PIN do konta Windows.

Workflow nie uruchamia się po pushu do brancha

Sprawdź, czy istnieje otwarty Pull Request do main i czy workflow reaguje na pull_request. Sam filtr push ograniczony do main nie obejmuje brancha roboczego.

Skrypt lokalnie zwraca Permission denied

Uruchom go jawnie przez bash scripts/check-repository.sh .... Ten sposób nie wymaga ustawienia bitu wykonywalnego i działa tak samo w pokazanym workflow.

Skrypt nie znajduje projektu, chociaż ścieżka wygląda poprawnie

Runner używa Linuksa, więc wielkość liter ma znaczenie. Porównaj wartość z wynikiem find . -name "*.csproj" i pamiętaj, że ścieżka jest liczona od katalogu głównego repozytorium.

Upload artifact zgłasza, że nie ma plików

Sprawdź, czy dotnet publish używa --output ./artifacts/app, a path w kolejnym kroku wskazuje dokładnie ten sam katalog.

Artefakt nie jest widoczny przy Pull Requeście

Otwórz konkretne uruchomienie workflow i jego stronę podsumowania. Artefakty są prezentowane przy runie, nie jako pliki w repozytorium.

Po błędzie następne stepy mają status skipped

To oczekiwane zachowanie. Step zwrócił kod różny od zera, dlatego GitHub przerwał dalsze wykonywanie joba. Napraw przyczynę w pierwszym czerwonym kroku.
