01

GIT / BRANCH

Utwórz gałąź funkcjonalną

Po co tworzymy osobną gałąź? Nie każda zmiana jest od razu gotowa. Kod może być rozpoczęty, wymagać testów albo czekać na konsultację. Gdyby każdy taki etap trafiał bezpośrednio na main, główna gałąź mogłaby zawierać niedziałającą lub niekompletną wersję projektu.

Branch funkcjonalny jest bezpiecznym miejscem na pracę w toku. Możesz robić na nim małe commity, eksperymentować i poprawiać rozwiązanie, podczas gdy main nadal wskazuje ostatnią uzgodnioną wersję. Dopiero gotową i sprawdzoną zmianę proponujesz do połączenia przez Pull Request.

Branch pomaga również przenosić pracę między stanowiskami. Przykładowo: rozpoczynasz zadanie w szkole, zapisujesz aktualny etap w commicie i wysyłasz branch na GitHuba. W domu pobierasz ten sam branch i kontynuujesz dokładnie od zapisanego miejsca. Push brancha nie oznacza połączenia go z main.

SCENARIUSZ

W szkole zmiana jest ukończona w 60%, ale zajęcia się kończą. Zamiast dodawać niegotowy kod do main, wykonujesz commit na feature/readme-contact i publikujesz ten branch. W domu pobierasz go, kończysz zadanie, a dopiero potem otwierasz lub aktualizujesz Pull Request.

W FIRMIE

Otrzymujesz zadanie dodania formularza kontaktowego. Tworzysz branch feature/contact-form, regularnie zapisujesz postęp w commitach i wysyłasz go na serwer, aby praca była dostępna dla zespołu. Gdy funkcja jest gotowa, otwierasz Pull Request. Inna osoba przegląda kod, proponuje poprawki, a automatyczne testy sprawdzają projekt. Dopiero po akceptacji i poprawnym wyniku testów branch zostaje połączony z main. Dzięki temu główna gałąź zawiera zmiany, które zostały sprawdzone, a zespół może równolegle pracować nad innymi zadaniami.

Utwórz gałąź o nazwie opisującej zmianę. git switch -c jednocześnie tworzy gałąź i przełącza na nią.

git switch -c feature/readme-contact
git branch --show-current

Dopisz na końcu pliku README.md dwie linie:

## Kontakt
Autor: Student
git diff
git add README.md
git commit -m "docs: add contact section"
git log --oneline -3

Commit zapisuje bieżący, sensowny etap pracy — nie musi oznaczać, że całe zadanie jest już gotowe do połączenia z main. W następnym kroku opublikujesz branch, aby commit był dostępny również poza tym komputerem.

    ✓
  • Aktualna gałąź to feature/readme-contact
  • git diff pokazuje dwie dodane linie przed commitem
  • Nowy commit jest pierwszy na krótkiej liście historii
02

GITHUB / PULL REQUEST

Opublikuj zmianę i otwórz PR

git push -u origin feature/readme-contact
  1. Otwórz repozytorium na GitHubie i wybierz Compare & pull request.
  2. Sprawdź ustawienie base: main oraz compare: feature/readme-contact.
  3. Wpisz tytuł docs: add contact section i krótko opisz zmianę.
  4. Otwórz zakładkę Files changed. Nie łącz jeszcze Pull Requestu.
SPRAWDŹ

Czy PR pokazuje dokładnie jeden plik i dwie nowe linie? Pull Request jest propozycją zmiany i miejscem przeglądu — nie osobną kopią repozytorium.

03

MODEL PRACY / GITHUB

Zrozum commit, branch i Pull Request

Zanim wywołasz konflikt, zatrzymaj się i sprawdź, co zostało utworzone. Te trzy pojęcia opisują różne elementy pracy:

commit
Zapisany punkt historii: migawka przygotowanych zmian wraz z autorem, datą, opisem i unikalnym identyfikatorem. Commit nie jest wysyłany na GitHub, dopóki nie wykonasz git push.
branch
Lekki wskaźnik na wybrany commit. Gałąź przesuwa się do kolejnych commitów podczas pracy. Nie jest pełną kopią katalogu ani osobnym repozytorium.
Pull Request
Propozycja włączenia zmian z gałęzi porównywanej do gałęzi bazowej. Łączy listę commitów, różnice w plikach, rozmowę i wynik przeglądu.
PRZEPŁYW

Edytujesz pliki → wybierasz zmiany przez git add → zapisujesz commit → wysyłasz branch przez git push → otwierasz Pull Request → przeglądasz i łączysz zmianę.

Wykonaj krótką analizę lokalnie:

git branch
git log --oneline --graph --all -8
git show --stat HEAD
    ✓
  • Gwiazdka przy git branch wskazuje aktualnie wybraną gałąź
  • git log pokazuje, na których commitach znajdują się gałęzie
  • git show --stat HEAD pokazuje autora, opis oraz pliki ostatniego commita

Teraz zbadaj te same obiekty w interfejsie GitHuba:

  1. Na stronie repozytorium otwórz listę gałęzi. Przełącz widok między main i feature/readme-contact.
  2. Na każdej gałęzi otwórz README.md. Sprawdź, dlaczego ten sam plik może mieć różną zawartość.
  3. Kliknij odnośnik z liczbą commitów. Otwórz ostatni commit i obejrzyj jego identyfikator, autora, komunikat oraz zmienione linie.
  4. Wróć do Pull Requestu. W zakładce Commits znajdź ten sam commit, a w Files changed zobacz łączny efekt całego PR.
  5. Otwórz widok porównania gałęzi i ustaw base: main oraz compare: feature/readme-contact. Zamień je miejscami i zobacz, jak zmienia się kierunek różnic.
ODPOWIEDZ

Czy branch zawiera pliki, czy wskazuje historię commitów? Czym różni się widok pojedynczego commita od Files changed całego PR? Dlaczego kierunek base → compare ma znaczenie?

04

GIT / KONFLIKT

Utwórz kontrolowany konflikt

Na gałęzi main zmień dokładnie tę samą linię, którą zmieniła gałąź funkcjonalna. To bezpieczna symulacja typowego konfliktu.

git switch main

W README.md dodaj lub zmień sekcję kontaktową tak, aby zawierała:

## Kontakt
Zespół: Warsztat Programisty
git add README.md
git commit -m "docs: add team contact"
git push

Wróć na gałąź funkcjonalną i spróbuj włączyć aktualny main:

git switch feature/readme-contact
git merge main
git status
    ✓
  • Git zatrzymuje scalanie i wskazuje konflikt w README.md
  • git status pokazuje plik jako both modified
05

GIT / NARZĘDZIA

Rozwiąż konflikt w edytorze

Najpierw otwórz README.md jako zwykły tekst. Zobacz, jak Git oznaczył wersję bieżącej gałęzi (HEAD) i wersję dołączaną z main:

<<<<<<< HEAD
Autor: Student
=======
Zespół: Warsztat Programisty
>>>>>>> main

Następnie uruchom narzędzie do rozwiązywania konfliktów w wybranym IDE. Nie klikaj automatycznie „Accept Current” lub „Accept Incoming” — najpierw ustal, która strona odpowiada bieżącej gałęzi, a która gałęzi main.

A / VS CODE

Merge Editor

W panelu Source Control wybierz konfliktujący plik, a następnie Resolve in Merge Editor. Porównaj widoki Incoming, Current i Result. Możesz też użyć akcji wyświetlanych bezpośrednio nad konfliktem.

Konflikty w VS Code ↗
B / RIDER

Resolve Conflicts

W oknie Commit znajdź sekcję Merge Conflicts i wybierz Resolve. Lewy oraz prawy panel pokazują wersje wejściowe, a środkowy panel — wynik.

Konflikty w Riderze ↗
C / VISUAL STUDIO

Merge Editor

Otwórz okno Git Changes, rozwiń listę Unmerged Changes i kliknij konfliktujący plik. Porównaj opcje Take Current, Take Incoming oraz ręczną edycję wyniku.

Konflikty w Visual Studio ↗
  1. Wybierz wersję bieżącą i zobacz, jak zmienił się panel wyniku. Cofnij ten wybór.
  2. Wybierz wersję dołączaną, ponownie obejrzyj wynik i cofnij wybór.
  3. Spróbuj przyjąć obie wersje. Zwróć uwagę na ich kolejność oraz powtórzenia.
  4. Na końcu ręcznie zbuduj jedną czytelną wersję, zapisz plik i sprawdź go przez git diff.

Końcowy wynik powinien zawierać informacje z obu gałęzi:

## Kontakt
Autor: Student — Warsztat Programisty
git diff
git add README.md
git commit -m "merge: resolve contact conflict"
git push
git status
    ✓
  • W pliku nie ma znaczników <<<<<<<, ======= ani >>>>>>>
  • Potrafisz wskazać w swoim edytorze wersję bieżącą, dołączaną oraz wynikową
  • Pull Request na GitHubie ponownie może zostać połączony
PORÓWNAJ

Obejrzyj ten sam konflikt w jeszcze jednym IDE u osoby obok albo na komputerze prowadzącego. Które narzędzie najlepiej pokazuje trzy wersje? Gdzie najłatwiej zbudować wynik z fragmentów obu stron? Czy nazwy „current”, „incoming”, „yours” i „theirs” są równie czytelne?

06

GITHUB / SQUASH

Połącz Pull Request jako jeden commit

Na stronie PR wybierz z listy Squash and merge, sprawdź komunikat końcowego commita i potwierdź. Ta metoda zbiera wszystkie commity PR w jeden logiczny commit na main.

Po połączeniu usuń zdalną gałąź przyciskiem Delete branch, a następnie zsynchronizuj lokalne repozytorium:

git switch main
git pull --ff-only
git branch -D feature/readme-contact
git log --oneline --graph -5
    ✓
  • main zawiera uzgodnioną treść README
  • Zmiana z PR jest widoczna na main jako jeden commit; -D usuwa sprawdzoną gałąź, której commitów squash nie zachował osobno
07

ANALIZA / STRATEGIE

Porównaj merge, squash i rebase

Merge commit

Zachowuje wszystkie commity gałęzi i dodaje commit scalający. Historia pokazuje moment połączenia dwóch linii pracy.

git switch main
git merge feature/nazwa

Squash merge

Łączy cały PR w jeden commit na main. Drobne commity robocze nie trafiają osobno do głównej historii.

# wybór na stronie PR:
Squash and merge
REBASE

git rebase main przenosi commity bieżącej gałęzi na aktualny koniec main, tworząc dla nich nowe identyfikatory. Daje liniową historię. Nie wykonuj rebase na współdzielonej gałęzi bez uzgodnienia z zespołem.

git switch feature/nazwa
git rebase main
git log --oneline --graph --all -8

04

ŚCIĄGA

Minimalny zestaw komend

git status
Pokazuje bieżącą gałąź, zmienione pliki i stan trwającego konfliktu.
git switch -c nazwa
Tworzy nową gałąź i od razu na nią przełącza.
git branch
Wyświetla lokalne gałęzie; gwiazdka oznacza gałąź bieżącą.
git diff
Pokazuje niezapisane różnice w katalogu roboczym.
git log --oneline --graph --all
Pokazuje skróconą historię i rozgałęzienia.
git merge nazwa
Włącza wskazaną gałąź do gałęzi bieżącej.
git merge --abort
Przerywa nieukończone scalanie i wraca do stanu sprzed próby.
git rebase main
Odtwarza commity bieżącej gałęzi na końcu main.
git rebase --abort
Przerywa nieukończony rebase i przywraca wcześniejszy stan.

ZADANIE DO WYKONANIA

Dodaj instrukcję uruchomienia

Samodzielnie przeprowadź drugą zmianę przez cały workflow:

  • Utwórz z aktualnego main gałąź docs/run-instructions.
  • Dodaj do README sekcję ## Uruchomienie z komendą dotnet run.
  • Wykonaj dwa małe commity: dodanie nagłówka oraz dodanie komendy.
  • Przed publikacją przeanalizuj git status, git diff i git log --oneline -3.
  • Wyślij gałąź i otwórz Pull Request do main.
  • W Files changed sprawdź, czy PR nie zawiera przypadkowych zmian.
  • Rozwiąż przynajmniej jeden konflikt w VS Code, Riderze albo Visual Studio i porównaj interfejs z drugim narzędziem.
  • Połącz PR przez Squash and merge, pobierz main i usuń lokalną gałąź.
DLA CHĘTNYCH / REBASE

Utwórz gałąź docs/requirements i zrób na niej dwa commity. Następnie dodaj osobny commit na main, wróć na gałąź i wykonaj git rebase main. Porównaj wykres historii przed i po poleceniem git log --oneline --graph --all.

06

DIAGNOSTYKA

Gdy coś nie działa

Zmiany trafiły na niewłaściwą gałąź

Nie twórz kolejnych commitów. Sprawdź git status. Jeśli zmiany nie są jeszcze zapisane, utwórz właściwą gałąź poleceniem git switch -c feature/nazwa — zmiany przejdą razem z Tobą.

git switch odmawia przełączenia

Masz lokalne zmiany, które zostałyby nadpisane. Zapisz je w commicie na właściwej gałęzi albo świadomie odłóż. Nie usuwaj ich na ślepo.

Nie wiem, które linie zachować w konflikcie

Porównaj obie strony znaczników i ustal końcową treść z autorem zmiany. Plik po rozwiązaniu ma zawierać poprawny wynik, a nie znaczniki konfliktu. Potem wykonaj git add i git commit.

IDE nie pokazuje edytora konfliktów

Najpierw sprawdź git status. Narzędzie pojawi się tylko podczas rzeczywistego, nierozwiązanego konfliktu. W VS Code zajrzyj do Source Control, w Riderze do Commit → Merge Conflicts, a w Visual Studio do Git Changes → Unmerged Changes. Możesz też zawsze rozwiązać plik ręcznie.

Chcę wycofać próbę merge lub rebase

Podczas merge użyj git merge --abort, a podczas rebase git rebase --abort. Następnie sprawdź stan przez git status.

GitHub nie pokazuje opcji Squash and merge

Właściciel repozytorium musi ją włączyć w Settings → General → Pull Requests. Jeśli nie masz uprawnień, użyj dostępnej strategii i opisz różnicę w wynikowej historii.

Po rebase zwykły push jest odrzucany

Rebase zmienia identyfikatory commitów. Na własnej gałęzi funkcjonalnej używa się wtedy ostrożnie git push --force-with-lease. Nie rób tego na main ani na współdzielonej gałęzi bez uzgodnienia.
